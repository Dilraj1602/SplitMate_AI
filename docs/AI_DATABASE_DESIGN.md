# AI Database Design

## `ai_pending_actions`

One row represents a prepared operation that still needs explicit user confirmation.

- `id`: UUID primary key and API action identifier.
- `user_id`: required foreign key to `users`, cascade deleted; scopes access to its owner.
- `action_type`: currently `CREATE_EXPENSE`.
- `payload`: validated JSON text used to revalidate and execute the operation.
- `preview`: JSON text generated by the backend for the confirmation UI.
- `idempotency_key`: unique key passed to the existing expense service.
- `status`: `pending`, `executed`, `cancelled`, or `expired`.
- `result`: persisted verified response used for duplicate confirmation.
- `expires_at`, `created_at`: action expiry and audit timing.

An index on `(user_id, status)` supports owner-scoped pending-action lookup. The table is additive and its Alembic downgrade drops only this table and index. Payloads are limited to the fields needed for the action; no prompts or full chat history are stored.

## `ai_conversations` and `ai_messages`

Conversations are owned by `users` and store a short JSON clarification context. Messages are owned through a cascading conversation foreign key and store user text or the structured assistant response. The API only lists and reads rows after checking conversation ownership. The graph consumes a bounded recent message window rather than loading the entire history. No vector index or financial record copy is stored.

Live financial data remains in existing normalized expense and settlement tables. The AI migration creates these tables and pending actions additively; its downgrade drops AI tables without touching existing product records.
